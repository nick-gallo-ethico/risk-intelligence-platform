````markdown
# System-Wide Entities Security Model

## Overview

This document describes the security model for entities with nullable `organizationId` in the Risk Intelligence Platform. These entities are intentionally designed to support both platform-wide resources and tenant-specific data.

**Audit Reference:** SEC-03 (Nullable organizationId RLS gaps)

## Architectural Decision

The platform uses Row-Level Security (RLS) via PostgreSQL session variables for tenant isolation. However, certain entities need to be accessible across tenants for shared platform resources. These entities use a **nullable organizationId** pattern with **application-level access control**.

### Security Model

| organizationId Value | Meaning                  | Access Control                                                                    |
| -------------------- | ------------------------ | --------------------------------------------------------------------------------- |
| `null`               | Platform-wide resource   | Application logic restricts write access; read access for all authenticated users |
| UUID                 | Tenant-specific resource | RLS + application logic restricts to matching tenant                              |

## Entities with Nullable organizationId

### 1. ReportTemplate

**Purpose:** Pre-built report templates for common compliance reports.

**Access Pattern:**

- `organizationId = null` + `isSystem = true`: Platform-provided templates (read-only)
- `organizationId = <uuid>`: Tenant-created custom templates

**Application-Level Controls:**

```typescript
// Query pattern
where: {
  OR: [{ organizationId: userOrgId }, { organizationId: null, isSystem: true }];
}

// Write protection
if (template.isSystem) {
  throw new ForbiddenException("System templates are read-only");
}
```
````

### 2. PromptTemplate

**Purpose:** AI prompt templates for various platform features (summarization, categorization, etc.).

**Access Pattern:**

- `organizationId = null` + `isSystem = true`: Platform-provided prompts (read-only)
- `organizationId = <uuid>`: Tenant-customized prompts

**Application-Level Controls:**

- System prompts cannot be modified via API
- Tenants can create organization-specific prompt overrides
- Query always includes system prompts plus tenant-specific prompts

### 3. ProjectTemplate

**Purpose:** Project management templates (implementation projects, compliance audits, etc.).

**Access Pattern:**

- `organizationId = null` + `isSystem = true`: Platform-provided templates
- `organizationId = <uuid>`: Tenant-created templates

**Application-Level Controls:**

- Same pattern as ReportTemplate
- `isSystem` flag prevents modification
- Tenants can clone system templates to create their own

### 4. AiContextFile

**Purpose:** AI context files containing domain knowledge for AI features.

**Access Pattern:**

- `organizationId = null`: Platform-level context (compliance regulations, best practices)
- `organizationId = <uuid>`: Tenant-specific context
- `userId` field: User-specific context within tenant

**Application-Level Controls:**

- Platform files visible to all during AI operations
- Tenant files filtered by organizationId
- User files filtered by userId
- Hierarchical loading: platform → org → user

### 5. QuizAttempt

**Purpose:** Training module quiz attempts for platform certifications.

**Access Pattern:**

- `organizationId` is nullable for cross-organization platform training
- Primary access control is via `userId`

**Application-Level Controls:**

```typescript
// Users can only see their own attempts
where: {
  userId: currentUserId,
  // organizationId not filtered - certifications are platform-wide
}
```

**Security Note:** Training certifications are platform-wide (not tenant-specific) because compliance certifications should follow users across organizations.

### 6. Certificate

**Purpose:** Certification records for completed training.

**Access Pattern:**

- Same as QuizAttempt
- `userId` is the primary access control
- `organizationName` stored for historical record

**Application-Level Controls:**

- Users can only view their own certificates
- Certificates are permanent records (survive org changes)
- Admin impersonation respects user scoping

### 7. KnowledgeBaseArticle

**Purpose:** Help center articles for platform documentation.

**Access Pattern:**

- `organizationId = null`: Platform documentation (visible to all)
- `organizationId = <uuid>`: Tenant-specific help content

**Application-Level Controls:**

```typescript
// Query pattern
where: {
  OR: [
    { organizationId: null }, // Platform articles
    { organizationId: userOrgId }, // Org-specific articles
  ];
}
```

## RLS Interaction

PostgreSQL RLS policies are configured to:

1. Allow queries where `organizationId` matches the session variable
2. Allow queries where `organizationId IS NULL` (platform resources)

The RLS policy for system-wide tables:

```sql
CREATE POLICY tenant_isolation ON report_template
  FOR ALL
  USING (
    organization_id = current_setting('app.current_organization', true)::uuid
    OR organization_id IS NULL
  );
```

## Audit Trail

All access to system-wide entities is logged via the AuditLog:

- `entityType`: The entity type being accessed
- `organizationId`: The user's organization (for cross-reference)
- `action`: CREATE, READ, UPDATE, DELETE
- `actorUserId`: Who performed the action

## Testing Requirements

Each entity should have tests verifying:

1. Platform resources (null orgId) are readable by all tenants
2. Platform resources cannot be modified by tenants
3. Tenant resources are isolated (cross-tenant access denied)
4. User-scoped entities (Quiz, Certificate) respect userId
