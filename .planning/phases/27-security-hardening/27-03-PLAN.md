  <action>
Add body-parser configuration with size limits to main.ts.

Add import at top:

```typescript
import * as bodyParser from "body-parser";
```

After `const app = await NestFactory.create(AppModule, { bufferLogs: true });`, add:

```typescript
// Configure body size limits for security (SEC-05)
// 10MB limit for JSON and URL-encoded bodies
// File uploads are handled separately by Multer with their own limits
app.use(bodyParser.json({ limit: "10mb" }));
app.use(bodyParser.urlencoded({ limit: "10mb", extended: true }));
```

Note: NestJS uses body-parser internally, but setting explicit limits requires manual configuration.
The body-parser package is already available as a dependency of @nestjs/platform-express.

Key placement: AFTER NestFactory.create but BEFORE app.use(helmet()) to ensure body parsing happens early.

NOTE on CSRF (SEC-04): After reviewing the auth implementation:

- JWT tokens are sent in Authorization header, not cookies
- This architecture mitigates CSRF by default (browser won't auto-send Authorization header on cross-site requests)
- Refresh tokens use httpOnly cookies BUT are only accepted at the /auth/refresh endpoint
- The /auth/refresh endpoint requires the refresh_token cookie AND validates the token signature
- This is sufficient CSRF protection for the current architecture
- Adding csurf middleware could break the API for SPA clients
- Decision: Document as "mitigated by design" rather than add CSRF middleware

<task type="auto">
  <name>Task 2: Document CSRF mitigation approach</name>
  <files>apps/backend/src/main.ts</files>
  <action>
Add a comment block in main.ts documenting the CSRF mitigation approach.

After the body-parser configuration, add:

```typescript
// CSRF Protection (SEC-04 - Mitigated by Design)
// ------------------------------------------------
// This API uses JWT tokens in Authorization headers (not cookies) for authentication.
// Browsers do not automatically send Authorization headers on cross-site requests,
// which inherently mitigates CSRF attacks for most endpoints.
//
// The refresh token endpoint (/auth/refresh) uses httpOnly cookies, but:
// 1. It requires a valid refresh_token cookie with correct signature
// 2. It only issues new access tokens, not perform state changes
// 3. The SameSite cookie attribute provides additional protection
//
// For SPAs, adding traditional CSRF middleware (csurf) would break the API flow
// since there's no server-rendered form to embed CSRF tokens.
//
// Decision: CSRF is mitigated by architecture rather than additional middleware.
```

This documents the security decision for future auditors.
